# Private feedback

Reporting is **off by default**, including production. Enabled deployments offer a floating **Send feedback** icon button to signed-in Supabase users, including while their garage is loading or recovering from a failure. Guests and Supabase anonymous users cannot submit. Reports go to a private Linear workspace; reporters need no Linear account.

## Deployment setup

Use `.env.example` as a reference; configure values separately in Vercel Preview and Production. All reporting settings are server-only, never `NEXT_PUBLIC_`.

Reports go to a separate free Linear workspace (for example "Garage Guardian Feedback"), not the workspace used for development. The Free plan caps a workspace at 250 issues, so spam can only fill the feedback workspace. It has two teams: `Feedback` (key `FB`) for Production and `Feedback test` (key `FBT`) for Preview and the smoke test.

| Variable                                             | Purpose                                                                                                                                                                                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FEEDBACK_ENABLED`                                   | Exact string `true` opts the deployment in; otherwise disabled.                                                                                                                                                                 |
| `FEEDBACK_LINEAR_API_KEY`                            | Linear API key restricted to the destination team, with Read and Create issues permissions. Add Write only if the smoke test shows screenshot upload (`fileUpload`) needs it. Use the `FBT` key in Preview, `FB` in Production. |
| `FEEDBACK_LINEAR_TEAM_ID`                            | UUID of the destination team (`FBT` in Preview, `FB` in Production). Redis keys are separated per team.                                                                                                                         |
| `FEEDBACK_HMAC_SECRET`                               | At least 32 random characters. HMAC domain separation derives reporter pseudonyms, issue IDs and private rate-limit keys. Keep stable across deployments that should share reporter IDs.                                        |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | Credentials for an Upstash Redis **Free** database. Do not upgrade it to a paid tier.                                                                                                                                           |
| `FEEDBACK_ENVIRONMENT`                               | Optional override of `VERCEL_ENV`; falls back to `development`. Letters, numbers, dots, underscores, hyphens only.                                                                                                              |
| `FEEDBACK_RELEASE`                                   | Optional release override. Default is package version plus `VERCEL_GIT_COMMIT_SHA`. Enabled Vercel deployments require the commit variable or this override.                                                                    |

A missing or malformed Linear key or team ID keeps reporting unavailable (`NOT_CONFIGURED`). The existing `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` verify bearer access tokens with `auth.getUser(token)`. No service role key or database migration is needed. Deployed IP limiting trusts Vercel's `x-vercel-forwarded-for`, not arbitrary client headers. Non-Vercel production hosting fails closed until a trusted proxy implementation is supplied. Local development groups IP limits under loopback.

## Who can see reports

Users review the complete report text and each screenshot, and can remove diagnostic entries or all diagnostics before sending. The form says, below the description, what the report includes. Nothing is uploaded while editing/reviewing. Issues and uploaded screenshots are visible only to members of the feedback workspace; nothing is published to the web, and reporters see only the issue identifier (for example `FB-12`).

This setup guards against two risks of the earlier public GitHub destination. Sign-up is open, so any signed-in user could have posted text and images that were public immediately under the maintainer's account. And screenshot upload needed a token with push access to the code repository, so a leaked deployment setting could have exposed the code. The Linear key can only read and create issues in one team of a separate workspace, and nothing reaches GitHub.

The report includes the description, pseudonymous reporter ID, release/commit, environment, browser/OS user-agent string, known route name without queries/fragments (vehicle routes use `/cars/[carId]` without the vehicle ID), active screen/dialog, viewport/pixel ratio, locale and online status. It includes up to 20 recent errors from the last five minutes: console errors, browser errors, rejected promises, and caught garage/catalog operations. Collection starts only after reporting is confirmed enabled for the signed-in account. Records remain in memory and are cleared on account changes/sign-out; earlier startup errors and errors before enablement are not retroactively recovered.

Diagnostic text is bounded and redacts recognizable tokens (including Linear `lin_api_` keys), credential assignments, emails, VINs and URL queries/fragments. Arbitrary logged objects and network request/response bodies are not serialized. Redaction cannot recognize every form of private data. Review remains necessary. Real Supabase user IDs, account emails, IP addresses, raw garage state, and authentication tokens are not automatic report fields. Users must remove personal data from their descriptions and screenshots themselves; there is no screenshot-content redaction.

Descriptions and diagnostics render as fenced literal text, preventing Markdown/HTML injection and accidental mentions. Attachment filenames are generic, and server image decoding/re-encoding removes image metadata.

## Validation, limits and failures

Descriptions: 10–5,000 characters. The form has no title field; the issue title is the first line of the description, truncated to 80 characters and prefixed with `[Feedback]`. The complete formatted issue must fit a conservative 65,536-character cap, reserving markup for two attachment URLs of up to 2,048 characters each. Oversized reports remain reviewable so users can remove diagnostics or shorten their description; the server rejects them before decoding or uploading screenshots. Up to two PNG/JPEG/WebP files, each at most 1.5 MiB; total multipart body at most 3.25 MiB, enforced during streaming. Images must match their declared type, decode successfully, contain one frame, and have at most 20 million pixels. Re-encoded files must also fit the file limit. Unknown fields, unsafe diagnostic content, malformed contexts and invalid timestamps are rejected.

Upstash sliding windows enforce 3 submissions per 10 minutes and 10/day per verified user, plus 10 per 10 minutes and 50/day per IP. Separate processing windows with the same limits run after bounded multipart validation/hashing and receipt lookup, before any Sharp decode/re-encode. All dimensions must pass. Configuration/status and submission attempts also have a 30/minute per-user control limit. Rejected/provider-failed attempts can consume limits. Matching completed or uncertain receipt replays skip image decoding and consume neither processing nor submission limits; the control limit still applies. Shared networks can hit the IP limit despite separate accounts. Rate-limit failures return `429` and `Retry-After`. Redis errors or SDK timeouts return `503`; there is no fail-open fallback. Redis rate-limit analytics are disabled.

Redis stores HMAC identifiers, expiring counters, locks, and submission receipts containing only a payload hash, state, timestamps, Linear asset URLs and the final issue identifier. Report content and image bytes remain outside Redis. Receipts last 24 hours; locks use a two-minute lease, exceeding the submission and status functions' 60-second execution limits. Keep those execution limits below the lease duration on other hosting platforms. Pseudonyms are stable references, not anonymous identities; Linear issues and attachments persist until handled in Linear.

Screenshots are uploaded with Linear's `fileUpload` mutation: the server requests a signed HTTPS upload URL, sends the re-encoded bytes there without the API key, and accepts only an `https://uploads.linear.app/...` asset URL. Linear requests have a 12-second timeout and refuse redirects; a GraphQL `errors` array counts as a failure.

One UUID identifies a reviewed draft across retries. Claims are atomic, and changed content under the same UUID is rejected. Successful attachments are reused after partial failures. Each draft's Linear issue ID is a UUID derived with HMAC from the team, account and submission ID, so reporters cannot predict it and every retry of the draft reuses it. If Linear rejects a creation, the issue is looked up by that ID before reporting a failure, so a retry after an earlier creation that did succeed returns the existing issue. Issue creation is preceded by a saved `creating` receipt. A timeout/5xx leaves an ambiguous receipt; status checks look the issue up by its ID in the destination team, including archived issues, and never automatically create another issue. If it is not found, status remains unknown. After an interrupted uploader's lease expires, a status check acquires a new lease and re-reads the receipt. If it is still `uploading`, it becomes `failed`, allowing a retry with saved attachments; active uploads and ambiguous issue creation remain frozen. Retry safety is limited to the 24-hour receipt window.

The UI preserves drafts when closed or on errors, but drafts are not written to browser storage and are cleared on sign-out, account changes or page reload. Unknown delivery states freeze edits and offer status checks. If a previously uncertain receipt disappears, or an unconfirmed attempt reaches the 24-hour retention window, the UI refuses to resend and warns the reporter not to send the same report again. No background crash monitoring or session replay is included.

## Preview smoke test and rollout

1. Create the feedback workspace with teams `FB` and `FBT`, and one API key per team, each restricted to its team with Read and Create issues. Keep Production `FEEDBACK_ENABLED=false` until step 5.
2. Configure a Vercel **Preview** deployment with reporting enabled, an Upstash Free database, and the `FBT` key and team ID. Production gets the `FB` key and team ID.
3. Sign in with a test Supabase account. Supply its current access token privately as `FEEDBACK_SMOKE_ACCESS_TOKEN` and the preview origin as `FEEDBACK_SMOKE_URL`. For previews with Vercel Deployment Protection, also set `FEEDBACK_SMOKE_BYPASS_TOKEN` to the project's [automation bypass secret](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation). The script forwards it as `x-vercel-protection-bypass` on configuration, submission, and status requests. Keep both tokens private; do not place them in URLs, paste them into tickets, or commit them.
4. Run `node scripts/smoke-feedback.mjs`. The script refuses HTTP origins and non-preview reporting environments. It sends synthetic text plus a generated green image, fails if the identifier is not `FBT-n`, verifies it against the receipt, and resends the same draft to confirm it returns the same identifier. The bypass token is optional for unprotected previews.
5. In Linear, open the `FBT` issue and verify the screenshot and all context fields. Confirm the screenshot URL does not open in a signed-out browser. If screenshot upload failed with a permission error, add Write to the key and rerun. Cancel the synthetic issue. Also exercise the real UI at desktop and narrow mobile widths: screenshot selection/removal, report preview, focus trap/return, layered dialogs and errors.
6. Run the [standard checks](contributing.md#checks). Only enable production after the real smoke test passes.

Automated tests use stand-ins for Linear, Upstash, and Supabase. Actual key permissions, Linear issue rendering and attachment privacy, shared Upstash rate limiting across instances, the real authenticated UI, and provider failures are only verified by this preview smoke test. Automated accessibility assertions do not substitute for an audible screen-reader check.

Upstash's [Free tier](https://upstash.com/pricing/redis) currently includes 500,000 commands/month and 256 MB. Several Redis operations are used per report/control request; command count is not report count. Free quotas/provider failures can make reporting unavailable without affecting garage saves. Check usage in the Upstash dashboard. Do not add a credit card/upgrade automatically.

To disable, set `FEEDBACK_ENABLED=false` in the target environment and redeploy/restart. Existing open browsers may retain their button, but server submission/status endpoints immediately reject requests on the new deployment. Rotate the Linear key/Redis token through environment settings and redeploy. Changing the HMAC secret changes pseudonyms, issue IDs and Redis keys; coordinate rotation with the retry window to avoid losing receipt access. Diagnose provider failures without logging tokens, request bodies, raw user IDs or IPs.
